# cutcaches

## What changes for the editor

Use **cutcaches** throughout Settings, menus, progress, errors, CLI help, MCP descriptions and guides. Use **cutcache** for one item. The proposed controls are **Save cutcaches**, **Next to media**, **In project folder**, **On cache disk**, and **Clear cutcaches…**. Keep the existing preference and read existing filenames in place. The terminology change alone should move zero bytes.

## Placement, lookup and portability

1. Extend the current resolver and catalog with an item kind, owner, and stable key. Keep the collision-safe recording keys. Use the existing digest for immutable transcript assets and the renderer’s input-and-settings digest for generated stills. Separate the on-disk namespaces for these kinds. A shared disk can hold one physical copy of identical transcript bytes while two projects retain independent bindings and edits. Count physical bytes once in the preview. [Location resolver](../Sources/MPCutCore/SidecarLocations.swift)
2. In **Next to media**, place a single-source asset beside its recording. For a multi-source asset, remember one anchor when it is first saved, using the multicam reference recording or the first contributing input in saved order. For an unbound import or generated item with no media anchor, use the saved project folder and show that destination. Keep untitled attachments durable in the draft store until their destination is available. **In project folder** uses a managed area beside the saved project. **On cache disk** uses the selected folder across projects. A later timeline reorder must never move the anchor.
3. On read, check all applicable destinations, the existing project or draft transcript store, and known prior locations. Keep read-only inspection free of file creation. For mutable analysis, use the freshest compatible group. For an attachment, the project requests **one exact SHA-256**. Try another verified copy on corruption or disconnection. A newer transcript with different bytes represents a different revision. Never substitute it or trigger a paid recognition run to open an existing attachment.
4. Add a versioned, location-independent attachment reference. Preserve the strict legacy path reader and the explicit recovery flow. On attach, first save, Save As or relocation, write and verify the assets for the document and its retained history **before** atomically publishing project references. An interrupted save must leave the previous project readable. Keep prior copies available. Offer **Save Portable Copy…** to collect the project and its referenced transcript assets, including undo and redo, beside the destination project so it opens on another Mac without the original catalog or cache disk. Disabling automatic analysis still permits opening and saving authored attachments. [Project save and history](../Sources/MPCutCore/CutHistory.swift) · [Project schema](schema/cut-v4.schema.json)

## Clearing and delivery

- Extend the existing preview with **Recording analysis**, **Project transcripts**, **Generated stills** and **Transcription jobs**. Show the recording or project name, actual folder, reclaimable bytes and the reason for retention. Default clearing removes reproducible data. Keep project attachments and their dependencies protected even during whole-cutcache removal. Removing authored attachments goes through the project’s detach and history lifecycle. Shared or offline ownership can be incomplete, so absence from the local catalog is insufficient evidence to delete an asset. [Current cleaner](../Sources/MPCutCore/SidecarCacheCleaner.swift)
- Ship the vocabulary and compatible interfaces first. Introduce `mpcut analysis cutcaches inspect|build`, `--no-cutcaches` and matching MCP names. Keep existing commands, flags, tool names, stored preferences and JSON fields as compatibility aliases. Follow with the resolver and transcript migration, then the remaining cache writers and the unified clearing UI. Update the desktop, CLI, MCP and standalone-provider contracts together where a manifest or receipt changes.
- Verify each kind across all nine write/read location combinations. Include duplicate filenames, the same transcript used by two projects, different edits to the same media, poor or missing source bindings, first save, Save As, portable copy on a clean machine, undo/redo, offline disks, corrupt newer copies, full disks, cancelled writes, simultaneous GUI/CLI saves, provider retry and clear during use. Confirm that legacy projects open without writes, exact transcript bytes round-trip, clearing leaves protected attachments readable, and exported files survive a scan. Benchmark size, warm open and repeated saves with a long transcript shared by several projects.
