# Video chat recordings and two-angle interviews

Design reviewed November 23, 2026. See the [editing guide](PARTICIPANTS.md) for the implemented workflow and the [verification report](VIDEO-CHAT-VERIFICATION.md) for measured accuracy, performance and platform coverage.

## What an editor should be able to do

| Job | Editing workflow | Deliverable |
| --- | --- | --- |
| Cut a two-person interview | Select the host and guest once, pin their sides, and switch between host, guest and both. Keep both microphones live. | An edited interview, with Fit or Fill chosen independently for each side. The same workflow accepts two ordinary synchronized cameras. |
| Extract a panelist | Select a person, review their appearances, choose a canvas size, gap color and audio source. | A continuous, synchronized movie. Camera-off cards may be included or replaced with the gap color. Offscreen time keeps its duration. |
| Edit a panel as multicam | Select any subset of the roster to create angles. Keep the original gallery and screen share available as optional shots. | Switchable participant angles sharing one clock. Render aligned angle media when another editor or NLE needs files. |
| Publish a redacted meeting | Mark a participant for blur or opaque cover in the original gallery, or omit them from a rebuilt panel. Inspect uncertain intervals before delivery. | A re-encoded picture with the selected treatment. Voice and caption removal are separate, explicit choices. |

## Model the tile, the person and the shot separately

A **tile** is a region of the recorded frame. A **participant** is an editorial identity that can occupy different regions over time. A **shot** describes which people, cameras or presentation sources appear in the output and where. A guest can move from a thumbnail to the main stage while their output position, ISO microphone and transcript identity all stay the same. A screen share is its own visual source. A shared room camera can have several speakers.

### TileTrail

TileTrail is a standalone Rust library for tracking participant tiles across layout changes in video recordings. Use `tiletrail` for both the Cargo crate and the sibling repository. Publish a Cargo crate with an explicit reuse license, public API documentation and redistributable fixtures. A Rust application should be able to add the crate, feed it frames from its own decoder and obtain tracks. Analysis runs offline. The CPU path is complete and supported on macOS, Windows and Linux from the first release. The optional GPU backend, C ABI artifacts and Swift bridge target Apple Silicon macOS first. CPU-only consumers can build the crate without GPU dependencies. Keep media decoding and OCR behind adapters so the library builds independently of FFmpeg and MPCut.

**Platform scope.** The first GPU release target is Metal on Apple Silicon macOS. List validated OS, architecture and backend combinations in each release. Keep OS-specific code in backend and adapter modules, with GPU support behind a Cargo feature. Run the hardware fixture and device-loss suite before enabling automatic GPU selection for another target.

| Requested mode | Startup | Device loss during a scan |
| --- | --- | --- |
| `auto` | Prefer the GPU on validated targets and workloads. Use CPU elsewhere or if GPU initialization fails. | Recover on CPU from the first uncommitted frame when its input can be replayed. |
| `cpu-only` | Start on CPU without initializing a GPU. | Continue on CPU. |
| `gpu-required` | Attempt the requested GPU, reporting an unvalidated target as a diagnostic. If initialization fails, return an error at the requested scan start. | Stop with an error and the first uncommitted frame as the resume point. |

The safe Rust API accepts a stream of borrowed frames with explicit pixel format, dimensions, row stride, presentation timestamp, rational time base and display geometry. Specify the lifetime of the frame buffer and validate its length and stride before reading it. Return observations, possible identity matches, confidence, coverage and change events. Support queries for the regions visible at a given time and every appearance of a participant in an interval. Publish a versioned result schema with a worked example so another editor can consume a saved analysis without running the detector.

### Library choices for the prototype

| Component | Choice and responsibility |
| --- | --- |
| Decoding | Reuse MPCut’s decoder. For a combined scene and participant scan, feed both analyzers from one sequential decode, at the resolution each needs. Other applications supply timestamped frames from their own decoder. |
| GPU measurements | Start with an optional `wgpu` backend, tested on Metal first, and a small set of WGSL compute shaders for downsampling, edge and gutter measurements, and per-tile appearance summaries. Return compact measurements to Rust. Start with bounded uploads of host frames. Evaluate decoder texture import where transfer costs justify the platform integration. [wgpu](https://wgpu.rs/) |
| CPU fallback | Implement the same measurements with plain Rust loops over borrowed image planes and explicit row strides. Use common fixture expectations for both backends. Keep layout thresholds, confidence, identity decisions and event ordering in one Rust tracker. |
| Assignment | Use the Kuhn–Munkres solver in the `pathfinding` crate to match visual appearances across a layout change. The tracker scores candidate pairs and supplies an explicit unmatched choice. After matching appearances, it can link a stage view and a simultaneous thumbnail to one participant. [Assignment solver](https://docs.rs/pathfinding/latest/pathfinding/kuhn_munkres/index.html) |
| Nameplate OCR | Evaluate `ocrs` as an optional adapter on cropped labels when geometry and appearance leave a return unresolved. Its current Latin-script coverage limits which names it can help with. Ship an adapter only if it reduces identity errors on representative recordings. [ocrs language support](https://github.com/robertknight/ocrs#language-support) |

Keep the initial vision logic small enough to test against annotated frames. Consider OpenCV for a specific operation if it improves results enough to justify packaging its native dependencies. Revisit CubeCL if maintaining equivalent pixel operations in Rust and WGSL becomes a substantial cost. It can compile shared kernels for GPU and CPU targets, with LLVM in the CPU path. [OpenCV Rust bindings](https://github.com/twistedfall/opencv-rust) · [CubeCL backends](https://github.com/tracel-ai/cubecl#supported-platforms)

**Backend decision.** On Apple Silicon, compare the borrowed-plane CPU path and the `wgpu` prototype on the same two-person interview and dense gallery. Measure elapsed time from decode through committed tracks, including conversions, uploads and readbacks. Check both paths against annotated seat swaps, ambiguous returns and change-event times. Prefer the GPU for supported workloads and select the CPU for input paths where end-to-end measurements show a regression. Use this comparison to decide whether to ship the prototype backend and which texture adapters are worth implementing.

On device loss, discard uncommitted measurements and retain the last committed tracker state. Apply the recovery rule for the requested mode. Specify when the caller can release input and how to resubmit host-readable frames if a lost texture was the only copy. If replay is impossible, return the exact resume point and mark remaining coverage incomplete. Expose the selected backend, fallback reason and transition timestamp.

For other languages, ship a thin, versioned C ABI over the same Rust implementation, with a public header and macOS native library artifacts first. Use opaque analyzer handles, fixed-width fields, explicit buffer ownership and structured errors. Contain Rust panics at the boundary. MPCut’s Swift wrapper feeds frames from its existing decoder and translates results onto the source clock. A small Python example using the C ABI demonstrates a second consumer. Version the Rust API, C ABI and serialized results separately so clients know which compatibility promise applies.

Release from the independent repo. On macOS, run the annotated gallery fixture on an Apple Silicon GPU and in forced CPU mode. Exercise both automatic and GPU-required mode with no usable GPU and with injected device loss during a participant swap. Assert the selected backend, diagnostics and exact resume point for each outcome. Verify fallback preserves track IDs and emits each event once. Exercise the native Rust API, a separately compiled C client and the Swift bridge. On Windows and Linux, compile every feature and run the CPU fixture through Rust and through a separately compiled C client linked against the locally built library. Exercise result ownership and release in that client. Distribute prebuilt C artifacts for Apple Silicon macOS first. Check timestamps, track associations and change events against the same expectations, with a declared tolerance for rectangle coordinates. Install the crate into a clean Rust consumer project on each OS and the macOS C artifacts into a clean C project as a release check. MPCut pins a released version and can build from a fresh checkout without a local sibling directory.

### MPCut integration

**MPCutCore.** Supply decoded frames and source identity. Desktop, CLI and MCP consume the same analysis through MPCutCore. Preview and export use the accepted tracks and one resolved shot plan. Store versioned machine results in a separate product in the existing source .cutdb analysis sidecar. Key it by source identity, stream, time base, origin, scan coverage and detector configuration. Store the editor’s durable participant IDs, accepted associations, geometry corrections, audio/speaker bindings, masks and shot decisions with the project. Make an edited project portable by carrying or packaging the accepted geometry it needs for rendering. Reopening after cache eviction must reproduce the approved edit. Validate old and new project versions against their schemas and test that projects without participant edits retain their current behavior. On relink or rescan, compare source identity and analysis versions and flag affected decisions for reconciliation.

**Coordinates and clocks.** Represent source intervals as half-open ranges on the actual presentation clock, including stream origin. Store boxes in normalized, top-left display coordinates with an explicit rotation and pixel-aspect transform. Keep sampled observations distinguishable from inferred intervals. A cut between layouts changes the box on a frame boundary. Only interpolate during confirmed continuous movement. Map group and edited-output occurrences through MPCut’s existing rational timeline mapping, including repeated and reordered excerpts.

## Detection and scene markers

1. Establish layout regions from persistent edges, gutters, backgrounds and alignment across nearby frames. Test asymmetric speaker view, centered incomplete rows and a presentation with a filmstrip alongside regular grids. Face detection alone misses camera-off cards and can mistake faces in slides for callers.
2. Track short runs of consistent geometry. At a reflow, match the old and new sets jointly using spatial continuity, recent appearance and optional local nameplate recognition. Treat borders, controls and captions as overlays. A display name is evidence and can be duplicated or change. Keep ambiguous matches reviewable. A newly visible unknown guest should be cheap to link to an earlier appearance.
3. Distinguish video, camera-off card, screen share, confirmed absence and unknown coverage. A static image is insufficient evidence of camera-off. An unreadable transition is different from a deliberate gap. Sample stable periods economically and refine candidate transitions against adjacent decoded frames. Measure missed short appearances before selecting a sampling policy.
4. Offer marker rules for **any**, **at least N**, or **all** participants changing. Let editors choose the event types: enter/leave, move/resize, camera-state change or a hard picture cut inside a tile. Group simultaneous changes within a short configurable settling window and count distinct participants for participant rules. For a rule about changed screen positions, count comparable slots instead: replacing A with B in one slot counts as one changed slot. Offer slot counts only across layouts with comparable slots. The initial frame establishes the baseline. The proposed denominator for “all” is the union visible immediately before and after a transition, restricted to the selected roster. Skip empty sets and mark uncertain coverage. For example, a four-person grid swapping two seats yields one marker for “at least two moved” and none for “all moved.” Normal talking, border flashes and changes inside a presentation should produce no layout markers.
5. Expose markers as reviewable scene candidates. The current native scene pass samples 64×36 pixels and MPCut groups its cuts into recurring views. Tap decoded frames before that reduction for tile bounds and small labels. Keep its results available alongside participant events. Run threshold changes against stored events without rescanning media. Make cancel, resume, partial coverage and source replacement visible in both scan modes.

## Review, transcripts and audio

Add a **Participants** inspector beside the source monitor. At the playhead, show boxes, labels and a roster including offscreen people. Selecting a row highlights the corresponding region. Provide next/previous appearance, next uncertain match and before/after views at a reflow. Let an editor draw or resize a box, split a track at the playhead, link a returning appearance, or mark a region as presentation. Edits have explicit time scope, support undo, and survive reopening. Preview the output composition beside the source when reframing or masking.

Bind a participant to an existing audio lane or source/stream and to one or more attachment-scoped transcript speaker IDs. Reuse existing sync offsets, lane colors, evidence review and transcript projections. Offer prefilled matches when metadata agrees and expose conflicts for confirmation. For an external ISO starting late, place its first sample at its synced time. If the recording contains only a meeting mix, offer that labeled mix or silence for an extraction. Separate microphone audio requires actual isolated media.

Selecting a word seeks to its projected occurrence and highlights the mapped participant at that instant. During playback, highlight mapped speakers for the active words, including overlap. An offscreen speaker lights up in the roster. Selecting a tile can filter the transcript to that person. Maintain a separate visual selection for the editor’s pinned participant. An optional “suggest dialogue switches” command should propose editable cuts with minimum hold time and choices for overlap, reactions and offscreen speech. Highlighting alone never changes the edit.

## Composition and export

Use one shot description for solo, side-by-side, fixed 2×2 and ordered flow. Each slot names a participant or camera, fit/fill, optional crop anchor and background. Preserve chosen ordering through source reflows. Default to fixed slots for interviews. Flow can compact on confirmed absence if the editor enables it. Save layout changes as timed decisions so an interview can open in two-up, go solo for an answer and return to two-up. For more people than available slots, require a selection or an explicit layout change.

**Choosing an appearance.** For a participant crop, prefer a confirmed stage appearance. Within the preferred role, hold the current appearance while available. When choosing among equal candidates, use the largest visible area, then stable appearance ID to break ties. Allow a time-scoped appearance override. If the pinned appearance disappears during the override, show the configured slot background. Preview and export resolve the same appearance.

**Repeated excerpts.** Source tracking corrections apply to every occurrence of the corrected interval. Timed group shots supply the default layout. An assembly occurrence can override that layout for its own playback interval. Resolve participant-wide masks on source appearances before cropping or composing, so the same mask applies in every occurrence and layout. Make the scope visible when editing.

**Redaction coverage.** Apply the chosen treatment to every appearance of the selected participant, including both stage and thumbnail and their nameplates. Removal from a rebuilt layout frees the slot. Between sparse analysis samples, absence is inferred. For privacy export, verify coverage on every contributing source frame, including frames previously marked absent by inference. When any appearance or its bounds remain unresolved, stop before publishing and identify the affected interval for correction. Allow the editor to choose an opaque full-frame cover for unresolved frames and show those intervals in preview.

For two ordinary cameras, resolve both sources at the same group time with their individual offsets, recording changes and gaps. For two crops of the same decoded gallery frame, share the decode. A missing angle gets its slot background. Keep audio policy explicit across a two-up shot: fixed program mix, selected ISO lanes, silence, or one designated primary for Follow. Reuse existing audio delivery and muxing. Picture masking and layout changes require re-encoding. Preview and export must resolve the same slot plan.

Offer two distinct multicam deliveries. **Virtual angles** reference accepted participant geometry against the source and allow editing before rendering. **Render angle media** writes one movie per selected participant with a common start, duration and configured canvas. Put the meeting mix on a single program lane by default when assembling these files as multicam. MPCut currently models one active picture angle per switch. Represent a two-up shot as an explicit composition choice and show a rendered program option for interchange formats without tested support for simultaneous pictures. Carry individual ISOs when requested. A standalone extraction can use the participant’s ISO, full mix or silence. Report the planned resolution, audio and duration before rendering. Preserve VFR timing or document the chosen output cadence and how source frames are selected. Upscaling a gallery crop cannot restore camera detail.

## Delivery order and acceptance

| Milestone | Result to review before proceeding |
| --- | --- |
| 1. Rust portability and detection feasibility | Run the Rust API in CPU mode against the same fixture on macOS, Windows and Linux, and run a separately linked C consumer on each OS. Review the end-to-end `wgpu` and plain Rust comparison on macOS, including seat-swap assignments, uncertain returns and mid-scan recovery, before building the editor. Annotate short, permissioned Zoom, Meet and Teams recordings plus deterministic synthetic fixtures. Cover reflows, borderless tiles, duplicate names, camera-off/on, leave/return, stage plus thumbnail, screen shares and overlay controls. Produce boxes, identity tracks and suggested markers for review, with separate measurements per layout. |
| 2. Editable participant extraction | Follow one person across a seat swap, resize, absence and return. Correct a mistaken association, reopen with the cache cleared, then export one full-duration movie at a chosen resolution. Include simultaneous stage and thumbnail appearances. Verify the default crop, a pinned thumbnail and its disappearance. Inspect output frames at every transition and check timestamps and gap color. |
| 3. Speaker and ISO integration | Use a late-start external ISO and an overlapping exchange. Confirm word selection, playhead highlights, offscreen speech, and repeated excerpt projection. Verify sample alignment and that the meeting mix appears only once. |
| 4. Layouts, masking and interview shots | Exercise solo, pair, fixed grid, flow and original-layout masking. Drive the same two-up shot with two independent cameras and then two participants from one recording. Repeat one source range as solo and two-up. Confirm that its source correction and mask apply to both occurrences while the layout override affects only its occurrence. Compare preview to rendered frames at switches, recording gaps and corrections. |
| 5. Multicam handoff and automation | Generate virtual angles from a subset, render aligned angle files, and reopen them in a fresh multicam project. Verify audio routing and shared timing. Expose the same plan and coverage diagnostics through desktop, CLI and MCP. |

For the feasibility review, record box overlap against hand labels, missed tiles, false tiles, wrong identity links, unmatched returns, event precision/recall, boundary error in source frames, manual corrections per recorded hour, end-to-end GPU and CPU scan speed, transfer time, peak host memory and peak GPU memory. Score identity swaps separately from uncertain matches. Measure ordinary speech with a static layout as a negative control. For opaque cover, include a one-frame return between sampled absences and simultaneous stage and thumbnail appearances. Inspect every decoded output frame against the known target regions for exposed pixels. Exercise both unresolved-frame outcomes: an interrupted export and publication with opaque full-frame cover. For blur, check that the effect covers all intended regions and nameplates. Benchmark a long call before promising interactive scan speed. Set numeric release thresholds from the pilot and the cost of correcting its actual errors.

**First decision.** Start with a host/guest interview inside a gallery recording. It exercises identity, corrections, ISO alignment, transcript highlighting, gap handling and two-up output in one short fixture. Use that same edit with two synchronized camera files to verify the compositor is genuinely reusable. Review this slice before extending automatic layout recognition across the full meeting corpus.
