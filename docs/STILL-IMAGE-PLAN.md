# Still images in MPCut timelines

## Release contract

Place a still in a regular sequence or multicam program, edit its duration and framing, and export it while copying eligible camera footage. The original image remains the editable source. Preview reads the image directly. Export generates video samples for the selected output duration. Each instant has one program picture. GUI, CLI, and live MCP clients edit the same project and receive the same export decision.

In a 30-second interview, replace seconds 8–12 with a photograph and insert a two-second title at the beginning. The result lasts 32 seconds. The photo plays at output [10, 14) over uninterrupted interview audio. A camera switch at interview second 11 still determines which camera appears after the photo. With safe picture joins, the report shows 26 seconds of copied camera, six seconds of generated stills, and zero camera encoding. The sound report states whether original packets copy and how the title's silence is produced.

### Minimum shippable behavior

Both operations, both timeline types, and all three authoring surfaces ship together. The cut line describes the minimum release gate. The implementation target includes the optional capabilities listed below as well. The minimum preservation matrix below is a proposed release decision. These rows are end-to-end requirements for the packaged GUI and CLI on supported hardware. They are not claims about current encoder compatibility.

| Required fixture | Picture result at verified safe joins | Sound result |
| --- | --- | --- |
| Progressive SDR ProRes 422, MOV, PCM | Insert and replace with matching generated ProRes. Prove retained camera sample payloads are identical. | Copy continuous original sound on replace. Insert sample-counted silence and preserve retained PCM samples. |
| Progressive SDR 8-bit 4:2:0 H.264, MP4, stereo AAC-LC | Insert and replace on a representative supported AVC configuration. Prove retained camera samples copy. Test a mid-GOP return separately. | Copy continuous AAC on replace. For an insert, provide a working path with copied camera and precisely timed sound, including explicit AAC-only conversion when copied AAC plus silence cannot be verified. |
| Rec.2100 HEVC Main10, MOV, separately tagged PQ and HLG fixtures | Insert an HDR photo and replace picture with an SDR card on each transfer. Require verified safe-join camera copy, decoded highlights above diffuse white, and matching output transfer. Exercise full HDR conversion separately. | Include continuous sound on replacement and the independently planned sound action on insertion. |

For all rows test a head title, interior insert, and interior replacement. Also export the same edits with video selected alone. A narrower first experiment triggers backend work on the failing row. Full movie conversion cannot qualify a camera-preservation row. HEVC SDR Main/Main10 MOV-family targets, other ProRes profiles, AV1 in MKV/WebM, AVC/HEVC in MKV, and additional 4:2:2 formats are individually gated extensions. Publish the tested profiles, encoder, sample-description changes allowed by the muxer, OS/hardware, and reader results for each enabled row. Keep existing non-still export capabilities available.

**Schedule cut line.** The full target includes persistent generated-span caching, standalone still-only timelines, independent fragment detach, and native interchange mappings. These can move independently if scheduling requires it. Their respective baseline behaviors are job-local temporary generation, using an existing video timeline as the format reference, editing a fragmented placement as a unit, and destination-specific conversion diagnostics. Fully covering a camera timeline with pictures remains supported even if standalone still-only creation moves. Protect v2 documents against silent loss in every reader from day one. The required static formats below, HDR/gain-map handling, per-window display status, the secondary program monitor, project round trips, fit/fill, relink, history, MCP parity and the matrix above belong to the minimum.

## Timeline rules

| Operation | Regular sequence | Multicam | Sound |
| --- | --- | --- | --- |
| Replace Picture | Anchor to source intervals within named clip occurrences. Allow one placement to span several clips. | Author on one Assets track in group time. Intersect with every retained assembly occurrence. | Follow the underlying audio plan, including microphone switches. |
| Insert Still | Insert a duration-bearing item at the sequence playhead. Split a source occurrence when necessary. | Insert one duration-bearing item in assembly order. Split only that occurrence. | Shift subsequent sound and picture together. Add silence on each existing output audio track. Video-only programs stay video-only. |

- Use exact rational time and half-open ranges. Replacement edges use actual presentation boundaries, including VFR. Inserts store exact duration and cadence. Require an integral frame count for CFR. Allow a short final sample on a VFR output only after the encoder, muxer, and reader pass an exact timing and seek test. At VFR insert creation request a cadence if none has been selected.
- **Trims are reversible in both editors.** Store authored replacement bounds. Intersect them with the current clip trim or multicam assembly selection at resolution time. Trimming a sequence occurrence [0, 10) down to [0, 4) hides its replacement [5, 7). Extending that same occurrence back to 10 restores the photo. A group replacement behaves the same when an assembly range widens. A hidden placement appears in the placement list with zero visible duration. Validate stored bounds against their source domain, including offline structural validation on open. Validate media extents when available.
- Reordering a sequence occurrence carries its replacement fragments. Splitting partitions authored coverage at the split, including hidden handles on each outer side. Assign the right half its own occurrence ID. Explicit occurrence deletion removes its owned fragments. Duplication creates independent IDs and edits. For a fragmented placement, list all fragments and let asset/framing changes apply to the whole placement. Optional detach turns a selected fragment into an independent placement in one undo step.
- Exclusive replacement coverage is per sequence occurrence or multicam group. Check overlap on authored intervals, including hidden coverage, so widening a trim can never introduce a conflict. Reject overlap atomically with conflicting placement IDs. Adjacent ranges are valid. An insert inside a replacement divides its visible time around the card. A replace request spanning an existing card reports its ID so the editor can edit the card directly.
- Moving an insert interprets its destination on the pre-edit timeline. Translate through removal and keep a drop within the item's original interval in place. Insert before the item beginning at a shared boundary. Resizing or deleting an insert ripples later items. Removing a replacement reveals the underlying picture.
- Materialize an implicit full-group assembly on its first assembly insertion. An insert has assembly time and no group/source coordinate. Group replacements repeat with the recording. A card placed in one assembled occurrence appears once. The angle monitors and group editing tools remain available at valid group positions.

## Project v2

Use the existing sequence `clips` array as the sole ordering authority. In v2 it contains typed entries. A source entry retains its existing document ID, file, bounds and replacement-audio provenance. An inline still entry owns its placement ID, asset ID, duration, cadence and framing. In multicam, the ordered `assembly` contains group ranges and the same inline still entry. Keep the omitted assembly's full-group meaning. Range occurrences continue to be addressed by index within a revision. No new persistent ID is needed for a group range.

Both project kinds gain an asset table and a replacement placement collection. An asset has a stable ID, path, display name and source fingerprint. A replacement has a stable placement ID, asset ID, framing, and either sequence fragments (source clip ID plus authored interval) or a group interval. Many placements may reference one asset. Resolve output positions on demand. Normalizing an insert's representation must never create a second ordering list or a duplicate placement object.

Persist a versioned program color policy in v2. Resolve it from the retained video format for copy-oriented work, or the explicit target for a conversion or still-only project. Record transfer, primaries, matrix/range, reference viewing conditions, diffuse white and the rendition/tone-map policy version. Copy-oriented exports require compatible camera descriptions across the edit. Mixing PQ and HLG camera spans needs an explicit common conversion target. Missing or conflicting HDR signaling requires an explicit interpretation before generating matching samples. Expose the resolved values in inspect, dry-run, MCP state and queued-job snapshots. Include the policy in generated-span cache keys. Per-window display settings belong to application preferences.

Read strict v1 documents and their history. Preserve existing sequence document IDs across save/reopen. Write v1 whenever the current state and retained history are v1-representable. Persist new fields only in v2. A redo-only still edit requires v2. A v1 multicam reopen reconstructs range indices from order. MCP clients refresh those indices from a new revision after a structural change. Test equal-valued repeated group ranges explicitly. [Existing project format](CUT-FORMAT.md)

Extend history deltas, reconstruction budgets, relative-path rebasing, Save As, source-collision protection, and deduplication to assets, typed items, and replacement fragments. Validate unique IDs, existing asset/occurrence references, coordinate domains, positive durations, rational overflow, and framing. Allow offline editing and relinking. A relink updates all uses of one asset in one history step. Protect paths referenced through undo/redo, including symlink aliases. GUI and CLI saves coordinate the revision check and atomic publication so simultaneous stale writes yield a recoverable conflict.

## Export architecture

### Generation eligibility and encoder boundaries

Make three independent decisions per join. First, can MPCut generate a still with a stream description the target writer and readers accept? Second, can the retained camera packets start/end safely there? Third, if an edge needs repair, does the existing Smart Trim predicate permit that source/container pair? Reuse the existing predicate for the third decision. Add a separate still-generation capability check for the first. Its inputs include target sample description, container, color/geometry, exact schedule, installed encoder, and writer support. Eligibility can extend to ProRes at safe joins while excluding repairs for other unsupported formats. Passing an edge predicate alone never certifies generated stills. [Current edge predicate](../Sources/MPCutCore/SmartTrim.swift)

The in-process edge implementation selects VideoToolbox for H.264/HEVC and libsvtav1 for AV1. AVC/HEVC eligibility is limited to qualifying MOV-family sources and MOV/MP4/M4V outputs, supported SDR 4:2:0 profiles and source/configuration checks. AV1 has distinct Matroska and hardware-decoder gates. ProRes has no edge encoder here. Full conversion runs the bundled FFmpeg helper as a subprocess and has its own supported settings. [Edge implementation](../Sources/PacketWriter/smart_edge.c) · [Helper execution](../Sources/MPCutCore/ReencodeProcess.swift) · [Conversion video settings](../Sources/MPCutCore/ReencodeVideo.swift)

Share image decoding, framing, color conversion, intended sample schedule, and reporting in MPCutCore. Keep the backend boundary explicit:

1. For preservation exports, first implement a helper-backed picture-only temporary clip. Feed normalized frames and their exact schedule to the helper, including the requested ProRes profile. Probe emitted packets, sample description, PTS/DTS, duration and independent start. Extend assembly to consume this media as a generated span. Verify the actual description transitions on both sides in the final container. If helper output cannot satisfy the required AVC row, implement a normalized-pixel input to the in-process AVC encoder and repeat the same tests. Existing source-frame edge repair remains a separate operation.
2. For full conversion, supply normalized still frames to the conversion graph before its final encode. Avoid a lossy intermediate encode/decode for each image. Use the conversion target’s canvas and color format. Build or extend the timed-frame input explicitly, including VFR. A repeated-frame helper command that assumes a constant nominal frame rate cannot establish VFR support.
3. For SDR input and HDR output, define the image-to-HDR transfer, reference white, primaries, range and metadata handling before enabling that target. Test patches in the final render and preview. Existing HDR camera conversion and the ability to write HDR tags are insufficient evidence for SDR still generation. Unsupported rows return format-specific diagnostics at preflight.

Check coded and display dimensions, pixel aspect, rotation, bitrate/profile constraints, decoder configuration, bit depth, chroma, color and timescale. Handle timecode and ancillary tracks explicitly. Reject a destination that cannot preserve required timing or metadata, with verified alternatives where available. Use a bounded temporary capability probe if needed. Revalidate emitted samples before atomic publication. Job-local cleanup, bounded memory, cancellation and source-identity checks are mandatory. A persistent cache, when shipped, keys on source content, framing/color policy, encoder build/settings, muxer and exact schedule, coordinates concurrent writers, and discards partial entries.

### Independent picture and sound on ordinary sequences

This is new architecture for regular still-bearing sequences. CutEngine currently builds one ordered array of ResolvedSegment values and passes those source ranges and track windows to the native writer. Splitting that array at every picture change can introduce AAC packet boundaries even where the sound is untouched. Multicam already resolves separate picture and sound before mux. [Sequence planner and writer](../Sources/MPCutCore/CutEngine.swift) · [Program sound resolver](../Sources/MPCutCore/MulticamSound.swift) · [Program mux](../Sources/MPCutCore/MulticamMux.swift)

Build a shared program plan on one output clock. Resolve each retained source occurrence into picture plus independent per-output-track sound spans. Apply replacements only to picture. Apply inserts to picture, track timing, and generated silence. Coalesce contiguous sound spans by source identity, stream, routing, source/output continuity and compatible presentation edits. Feed the resulting picture plan and per-track sound plans to a writer/mux adapter. Preserve ordinary multitrack order, replacement-audio provenance, delayed starts, priming, layout and timecode. Extend the mux adapter for multiple independent output audio tracks. Never reduce an ordinary multitrack project to multicam's selected program microphone. Keep the existing linked writer for existing edits where appropriate.

First regression fixture: place a photo whose edges fall inside AAC packets over uninterrupted sound in an ordinary sequence. Require identical retained AAC payloads and presentation edits, and the same decoded sample timeline as the export without the photo. Repeat with two audio tracks and a replaced soundtrack. A picture join cannot force a sound cut.

### Silence and the H.264/AAC title gate

MulticamSound validates silent AAC windows backed by indexed source media and rejects a wholly empty AAC presentation. Its input spans require a source and stream. An inserted card has neither. Test authoring silence as new work. [Existing sound behavior](../Sources/MPCutCore/MulticamSound.swift)

- Represent silence explicitly per output track. For generated/converted sound, compute sample counts from rounded cumulative output endpoints. Five 1001/30000-second frames at 48 kHz span 8,008 samples. Copy paths keep their stricter packet, decoder-history, and sample-alignment rules. [Cumulative conversion timing](../Sources/MPCutCore/MulticamAudioConversion.swift)
- In the first evidence pass, test front, interior and tail titles in H.264/AAC MP4 and MOV. Include AAC-LC priming, a delayed start, packet-aligned and nonaligned returns, and a duration crossing a fractional sample boundary. Try a muxed empty presentation edit with copied AAC; verify actual reader playback and seeking. A generated AAC silence segment requires separate proof of compatible configuration, priming, padding and decoder continuity. Record which technique, container and reader passed.
- If a copy-preserving sound plan fails, return a track-specific reason for strict audio copy. Implement a hybrid writer path that copies eligible camera picture while explicitly converting only the affected sound track to AAC or compatible PCM. Today multicam conversion alternatives use Re-encode; this path requires new planning, muxing, export rules, and user-visible audio actions. Make it a release gate for the required AAC fixture. Verify silence, the first audible transient, sample count and unchanged camera packets. Report exactly which original audio was converted. Offer full conversion separately.

### Modes and reports

- For saved sequence or multicam project export with visible stills and a selected picture stream, default an omitted mode to Smart Trim. Show verified alternatives when the exact edit cannot use that mode. Explicit copy continues to reject generation and points to the actual eligible Smart Trim or conversion request. Preserve existing defaults for selections without visible still picture. An audio-only selection that needs generated silence follows audio eligibility and explicitly offers conversion. Cover omitted mode, explicit mode, stdin, CLI dry-run, MCP render, GUI defaults/preferences, and queues with parity tests.
- Add placement-aware rows to ExportRules for video-only generation in ordinary and multicam projects, and single-type sound conversion where supported. Regenerate the rules reference and test both resolvers. Keep the True Lossless tier available only when every selected output packet copies. Report generated-picture and sound actions in tier factors, prompts, and alternatives. [Current export matrix](EXPORT-RULES.md)
- **Preserve camera picture** and proposed CLI flag `--require-camera-copy` require zero encoded camera duration and preservation of the retained camera sample payloads. On long-GOP material an arbitrary return commonly depends on hidden pictures. Expect the boundary-review path. Identify the offending end of the still, show the nearest verified return with its duration change, replan both joins and all selected tracks, and apply only on explicit acceptance. If neither nearby boundary works, say so. Exact Smart Trim may encode the camera edge when eligible. An explicit preservation request must never silently take that alternative.
- Include exact `copiedCameraDuration`, `encodedCameraDuration`, and `generatedStillDuration` in GUI, CLI and MCP reports. Their sum equals selected output picture duration. Preserve existing aggregate copy/encode fields, including generated video in the encoded total. Show placement IDs, clocks, resolved ranges, join actions, per-track audio actions, and output duration. Audio-only preflight should ignore offline image pixels whenever its timing is independently resolvable. Pin settings and source identities when queuing.

## Modern still formats

Ship static JPEG XL (.jxl, bare codestream and container), AVIF, WebP, HEIF/HEIC, JPEG, PNG and TIFF through one shared import path. Accept lossy and lossless JXL, high-bit-depth and HDR JXL/AVIF, alpha where defined, and tagged wide-gamut SDR images. Decode JPEG and HEIC adaptive HDR gain maps, including Apple and ISO variants with fixtures for each supported encoding. Apply the gain map once. A 10-bit file or Display P3 ICC profile alone establishes neither HDR content nor an active HDR display.

Detect the primary image, its actual codec, orientation, ICC or signaled color characteristics, precision, alpha, auxiliary data and transfer before committing a placement. Use Image I/O when it can recover the required representation. Probe with actual fixtures on the macOS 14 deployment floor and the current OS. On this development Mac, the system image format list includes JXL, AVIF, WebP and HEIC. A development-host smoke check on macOS 27.0.1 also decoded the libjxl PQ-gradient and extended-size-container fixtures to 1088×64 and 8×8 PNGs via sips. This establishes raster decode on that OS. Precision, gain-map reconstruction, packaged-app decoding and macOS 14 compatibility have separate acceptance tests. [JPEG XL test data](https://github.com/libjxl/testdata/tree/main/jxl)

If a required variant loses its transfer, gain map or precision, use a pinned, packaged decoder for that variant (for example libjxl for JXL), with identical GUI, CLI and MCP results. Include the decoder in licensing and bundle checks. Inspect the actual image count and distinguish auxiliary items from animation or independent pages. Surface unsupported animations as a typed error. Add picker filters, file drop, relink, inspect output, thumbnail generation and packaged-binary fixtures for every advertised type. [Apple HDR image decoding and adaptive gain maps](https://developer.apple.com/videos/play/wwdc2024/10177/)

Before enabling a decoder path, compare the same reference image through native decoding and any bundled fallback. Cover JXL codestream and container, lossless RGB, high-bit-depth gradient, ICC-tagged SDR, explicit PQ, orientation and alpha. Include AVIF with color signaling, HEIC with a primary image and auxiliary data, and a genuinely animated WebP rejection. Verify premultiplied alpha against known edge pixels after linear-light compositing. Test malformed/truncated input and oversized dimensions within the same allocation limits. Exercise Finder open, Add Clips, drop, CLI and MCP on both the oldest supported OS and the shipping test host. Verify source rendition, precision and headroom before tone mapping; an 8-bit SDR thumbnail is insufficient evidence.

## HDR from source to program monitor

**Current implementation.** ReencodeVideo recognizes PQ and HLG, configures an eligible 10-bit target and forwards color characteristics. Packet copying can retain eligible original HDR streams. Smart Trim currently excludes PQ and HLG edge generation. Both editors use a sample-buffer display surface that can receive decoded pixel buffers. The inspected code does not establish per-window HDR status, a verified external HDR program feed, or preservation of dynamic mastering metadata through an encode. Treat those as release work. [Conversion setup](../Sources/MPCutCore/ReencodeVideo.swift) · [Smart Trim eligibility](../Sources/MPCutCore/SmartTrim.swift) · [Preview surface](../Sources/MPCutApp/Preview.swift)

**Program color pipeline.** Resolve source rendition and timeline/output color separately from the display. Decode HDR images to extended-range linear pixels at adequate precision. Keep color primaries, transfer, range and source headroom through crop, fit, transparency and compositing. Use a defined Rec.2100 reference viewing transform for HLG and absolute luminance for PQ. Adopt 203 cd/m² as the proposed HDR program diffuse white for SDR artwork, with no invented highlights in the card. Convert an HDR still to SDR using one documented, deterministic highlight roll-off and gamut mapping. Tag each generated 10-bit HDR sample description and stream accurately. Verify encoded pixel values independently of tags. Use the identical project color policy in headless export. Screen brightness, connected monitors and an optional SDR preview override must have no effect on export. Validate static mastering metadata against the assembled program. If copied or generated segments cannot produce valid Dolby Vision/HDR10+ dynamic metadata, identify that limitation in preflight and offer verified base-layer output only as an explicit choice. Check that the profile actually has an independently usable base-layer interpretation and that stripping dynamic metadata yields valid samples and signaling. If either check fails, refuse that alternative. For the camera-preservation guarantee, compare retained elementary-stream picture payloads after normalizing container framing. A base-layer conversion that rewrites or strips in-band camera metadata must be reported as a distinct conversion and cannot satisfy this guarantee, even if no frame was re-encoded. Distinguish mastering-display metadata from content-light statistics: retain verified mastering information where applicable and recompute or omit optional content-light values that the new still invalidates. [Existing packet-writer metadata checks](../Sources/PacketWriter/writer.c)

**Secondary monitor.** Extend the existing **View → Show Video Monitor** command and its MCP counterpart, `set_video_monitor`. ProjectSession.showMonitor already opens one VideoMonitorPanel per project, prefers a second screen, supports full screen, and hosts either preview. Keep this lifecycle and connect each hosted surface to the shared program-picture resolver. Give the editor viewer and pop-out separate rendering surfaces and screen state. Opening, closing or moving it must neither restart playback nor create a second audio player. Support full-screen output on a chosen display. Keep the last program frame while paused and rerender it immediately when the window changes screens, the display profile or headroom changes, or a monitor disconnects. The same screen-change handling applies to the embedded preview. Both existing preview engines choose a playback clock using the fastest attached screen. Keep that clock choice independent of the per-surface color decision. Test a faster SDR editor screen playing beside a slower HDR monitor and the reverse arrangement. Provide a clean-feed option that hides chrome on the pop-out while leaving its status accessible in the editor. Exercise two open projects, monitor close/reopen, and switching between ordinary and multicam modes in one session. [Existing monitor and hosting view](../Sources/MPCutApp/ProjectSessions.swift) · [Monitor command](USAGE.md)

**Per-window status.** Show a small text badge beside each viewer. Use **HDR · PQ** or **HDR · HLG** for HDR program output through a verified extended-range surface when the window's screen has current EDR headroom above 1. Use **SDR preview** for an HDR program mapped into SDR on that surface, and **SDR** for an SDR program. The tooltip and accessible label identify source rendition, program transfer, display, and any reason for tone mapping. SDR artwork on an HDR timeline keeps the program's HDR badge; the inspector identifies the SDR source. While display state is unresolved show a pending status. Enable/request extended range before checking current headroom and refresh on window/screen parameter changes. Query the screen containing that window rather than the main screen. Avoid double tone mapping when system presentation already performs it. [Apple’s per-screen EDR headroom behavior](https://developer.apple.com/documentation/appkit/nsscreen/maximumextendeddynamicrangecolorcomponentvalue)

Drive the badge from the actual presentation route for that surface. A screen can supply EDR headroom to another application while MPCut is presenting an SDR buffer. A forced SDR preview must still say **SDR preview** on that screen. A failed or untagged presentation shows an unavailable/unknown state until an explicit SDR fallback succeeds. Inspect buffer precision and transfer attachments on native, fallback, and still paths. Keep the shared program frame immutable and do per-window adaptation at presentation, so the SDR viewer cannot clip the HDR viewer’s input. Include forced SDR, hidden/minimized windows and screen reconnection in the state tests.

**Color acceptance.** For the proposed 1,000 cd/m² HLG reference configuration, neutral diffuse white should measure approximately 75% HLG signal. For PQ, 203 cd/m² corresponds to about 58% PQ signal. Compare normalized signal after accounting for legal/full range. Set fixture-specific tolerances before running the encoders, use flat patch interiors, and require distinct highlight steps above diffuse white in the HDR fixture. SDR cards stop at their intended white. For SDR review JPEGs, apply the documented SDR rendition once and encode sRGB. Keep the existing source/angle JPEG extraction semantics and use the composed program picture for explicitly program-addressed frames. [ITU guidance on HDR reference white](https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-2017-PDF-E.pdf) · [Current JPEG renderer](../Sources/MPCutCore/JPEGExport.swift)

**Release evidence.** Exercise HDR JXL, PQ/HLG AVIF or HEIC, gain-map JPEG/HEIC, an SDR P3 control, and SDR WebP with alpha. Compare decoded linear patches, white level, highlight detail and gamut within declared codec tolerances, including SDR → HDR and HDR → SDR. Physically test an HDR and SDR monitor simultaneously in both window arrangements, then move the paused and playing pop-out, toggle full screen, change headroom and disconnect the display. Check picture, badge and continuous audio in regular and multicam projects. Screenshots and simulated headroom alone cannot certify emitted HDR light. Capture display configuration and a reference HDR ramp measurement or instrumented comparison against a known-good HDR presentation. Verify identical exported frame values on an SDR-only or headless system.
